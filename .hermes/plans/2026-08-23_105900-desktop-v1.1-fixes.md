## Contexte — ce que j'ai trouvé

### 1. Réglages (DesktopSettings.tsx)

**Problème A — Projets manquants :** La prod a 6 projets (Frip & Trend, My Flip, Web@cadémie, Perso, Sport, IA) mais l'écran Réglages les affiche depuis `projects` (la liste du store). Le projet "Fake" n'existe pas dans `projects.json` — c'est un calendrier Apple supplémentaire (`EXTRA_AGENDA_CALENDARS = ["Fake"]` dans `caldav.ts`) qu'Aramis utilise pour poser des tâches. Les tâches du calendrier "Fake" sont adoptées par Brief mais arrivent sans projet (`projectId` vide) ou dans le projet de repli. **Solution : ne pas ajouter "Fake" comme projet Brief, mais s'assurer que les tâches qu'Aramis pose dans le calendrier "Fake" sont bien synchronisées et visibles.**

**Problème B — Couleurs fausses :** Les couleurs CSS (`--color-p1` à `--color-p6`) sont correctes (vérifiées le 22/08 contre Apple Calendar). Le problème vient du fait que l'écran Réglages affiche `skinFor(p)` qui lit `--color-p{tint}` — ces couleurs SONT les bonnes. Mais Aramis voit des couleurs fausses → vérifier si le problème vient du fait que les pastilles sont trop petites (12px) pour distinguer le bleu (#007AFF) du vert, ou si le shape (disc vs square) ne rend pas correctement. **Hypothèse : le problème visuel vient de la taille 12px et du manque de label de couleur.**

**Problème C — "Jetons du design system" à supprimer :** Le bloc en bas à droite (swatches, Aa, radius) est un artefact de démo du prototype Claude Design. N'a rien à faire en prod. → Supprimer.

**Problème D — Nom "Ia" au lieu de "IA" :** Le projet `ia` a `name: "Ia"` dans `projects.json` (mauvaise casse). Doit être "IA".

### 2. Tâches (DesktopTasks.tsx)

**Problème A — Priorités fausses :** Toutes les tâches ont une priorité (1-4) parce que le parseur LLM (`/api/parse`) assigne `priority: 3` par défaut et `priority: 4` comme fallback (`isPriority(r.priority) ? r.priority : 4`). Aramis n'a pas défini ces priorités lui-même → elles sont inventées. **Solution : ne pas afficher les priorités si elles n'ont pas été explicitement définies par l'utilisateur.** Options :
  - (a) Ne pas afficher le badge `p{N}` sur les tâches (juste le titre + la date)
  - (b) Ajouter un champ `prioritySet: boolean` sur les items, afficher le badge seulement si `true`
  - **Recommandé : (a)** — simplest, YAGNI. Tant qu'Aramis n'a pas assigné de priorités, on n'affiche rien. La colonne "Par priorité" à droite devient vide ou disparaît.

**Problème B — Tâches stale ("Faire des pâtes", "Tester le micro") :** Ces 2 tâches sont actives, sans `due`, sans `externalUid` — ce sont des items Brief purs, pas adoptés de CalDAV. Le sync CalDAV ne les complète que si elles ont un `caldavSyncedDue` et que l'événement a disparu. Ces items n'ont jamais eu de `due` → le sync ne les touche pas → elles restent actives pour toujours. **Ce n'est pas un bug du sync, c'est un problème de données : Aramis les a supprimées de son Calendrier Apple mais comme elles n'avaient pas de `due`, Brief ne les a jamais marquées `doneAt`.** Aramis dit "ce sont des tâches qui ne sont plus dans le calendrier Apple" → il faut les marquer `doneAt` manuellement (nettoyage de données) ou laisser Aramis les cocher. Ce n'est pas un bug du code, c'est un nettoyage ponctuel.

## Risques et tradeoffs

- **Retirer les priorités** : si Aramis veut plus tard les réintégrer, le code est encore dans l'historique git. Le modèle de données (`Item.priority`) n'est pas touché.
- **Mapping calendrier côté client** : créer `calendarMapping.ts` introduit une duplication du mapping (aussi dans `caldav.ts`). Le mapping change rarement (dernière fois le 18/08). Acceptable.
- **Tâches stale** : marquer `doneAt` sur les 2 items cités est ponctuel. Si le problème revient (tâches sans `due` qui restent actives), il faudra un mécanisme automatique (ex: marquer `doneAt` après X jours sans `due`). Pas maintenant.
- **Calendrier buggé** : reporté, pas touché. Risque : Aramis le redemande vite. Mettre dans TODOS.md avec priorité.
